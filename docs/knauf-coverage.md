# Thomas Knauf SeaTalk1 command coverage

This matrix compares every distinct command documented in Thomas Knauf's
*SeaTalk Technical Reference*, revision 3.22 (9 May 2014), with the current
transmit scope of this plugin. It is a coverage and safety decision record, not
a claim that Knauf's reverse-engineered list defines every possible SeaTalk1
command. Knauf explicitly warns that the information may be incomplete or
inaccurate.

## Status meanings

| Status | Meaning |
| --- | --- |
| Implemented | The plugin has a tested encoder and a documented Signal K input or managed feature. |
| Candidate | Technically plausible, but a reliable external source, ownership policy, loop prevention, and vessel test are still required. |
| Redundant | An implemented command already carries the required information, or the command duplicates another documented form. |
| Device-owned | This identifies, configures, or reports the state of real SeaTalk equipment and must not be impersonated by this converter. |
| Safety boundary | It operates an autopilot, acknowledges or creates an alarm, changes safety state, or injects route-control state. |
| Insufficient definition | Knauf marks the meaning unknown or the available definition is not sufficient for safe generation. |

## Complete command matrix

| Command | Knauf meaning | Status | Current decision |
| --- | --- | --- | --- |
| `0x00` | Depth below transducer and alarm flags | Candidate | A Signal K depth path exists, but the vessel already receives depth from SeaTalk. Sending it back would create a loop or competing talker unless external-source ownership is resolved. |
| `0x01` | Equipment identity at power-up | Device-owned | The plugin is not a physical SeaTalk instrument and must not claim a hardware identity. |
| `0x05` | Engine RPM and propeller pitch | Candidate | Requires validated propulsion-instance selection, signed pitch semantics, source ownership, and a vessel test. It is outside the current navigation/wind scope. |
| `0x10` | Apparent wind angle | Implemented | Encoded from `environment.wind.angleApparent`; Signal K radians are converted to half-degree clockwise angle right of bow. |
| `0x11` | Apparent wind speed | Implemented | Encoded from `environment.wind.speedApparent`; Signal K m/s is converted to knots. |
| `0x20` | Speed through water, tenths of a knot | Candidate | The existing SeaTalk log is normally the source. Retransmission would echo it; an external STW source needs an explicit priority and loop policy. |
| `0x21` | Trip mileage | Candidate | No current, validated external Signal K trip-log source has been selected. The installed SeaTalk log already owns this value. |
| `0x22` | Total mileage | Candidate | No current, validated external Signal K total-log source has been selected. The installed SeaTalk log already owns this value. |
| `0x23` | ST50 water temperature | Candidate | The current vessel value is SeaTalk-originated and has shown implausible input, so transmitting it would amplify bad or looped data. Prefer `0x27` for any future external source. |
| `0x24` | Display units for mileage and speed | Implemented | Managed by the display-unit synchronizer, which rejects incoherent mixed unit systems. |
| `0x25` | Combined total and trip log | Candidate | Same source-ownership issue as `0x21`/`0x22`; no reliable external log source is configured. |
| `0x26` | Extended speed through water | Candidate | More expressive than `0x20`, but requires sensor-validity, average-speed, second-sensor, and unit policies that current Signal K inputs do not establish. |
| `0x27` | Water temperature, tenths of a degree | Candidate | Suitable only after selecting and validating an external temperature source and preventing echo of SeaTalk-originated data. |
| `0x30` | Display lamp intensity | Implemented | Managed as levels L0–L3 with duplicate suppression and rate limiting. |
| `0x36` | Cancel MOB condition | Safety boundary | Clearing a man-overboard condition is an explicit safety action and is never generated by this plugin. |
| `0x38` | Codelock data | Insufficient definition | Proprietary codelock semantics are not sufficiently defined and have no Signal K mapping. |
| `0x50` | Filtered latitude | Implemented | Encoded from `navigation.position.latitude`. |
| `0x51` | Filtered longitude | Implemented | Encoded from `navigation.position.longitude`. |
| `0x52` | Speed over ground | Implemented | Encoded from `navigation.speedOverGround`; Signal K m/s is converted to tenths of a knot. |
| `0x53` | Magnetic course over ground | Implemented | Derived from true COG and magnetic variation with range and normalization checks. |
| `0x54` | GMT/UTC time | Implemented | Encoded from `navigation.datetime` in UTC. |
| `0x55` | TRACK key on a GPS unit | Safety boundary | Key injection could change navigation or autopilot behavior and is outside passive data output. |
| `0x56` | Date | Implemented | Encoded from `navigation.datetime` with representable-year validation. |
| `0x57` | Satellite count and HDOP | Implemented | Encoded from `navigation.gnss.satellites` and `navigation.gnss.horizontalDilution`. |
| `0x58` | Raw, unfiltered latitude/longitude | Redundant | `0x50`/`0x51` provide the documented stable filtered position expected by instruments; a second position form would add bus load and ambiguity. |
| `0x59` | Set/start countdown timer | Safety boundary | This is a remote control operation, not conversion of navigation data. |
| `0x61` | E-80 initialization message | Device-owned | A device-specific initialization signature must not be synthesized. |
| `0x65` | Select fathom depth units | Safety boundary | It changes instrument state and only coheres with `0x00`, which is not transmitted. |
| `0x66` | Wind alarm state | Safety boundary | Fabricating or clearing alarms is unsafe; Signal K alarm lifecycle and acknowledgment semantics are not equivalent. |
| `0x68` | Alarm acknowledgment key | Safety boundary | Alarm acknowledgment requires an intentional operator action on the responsible system. |
| `0x6C` | Second equipment identity | Device-owned | As with `0x01`, the converter must not impersonate installed hardware. |
| `0x6E` | Man overboard | Safety boundary | MOB creation/propagation needs a dedicated, fail-safe safety design and is outside this plugin. |
| `0x70` | ST60 Maxiview remote-control keys | Safety boundary | Arbitrary remote key injection is explicitly excluded. |
| `0x80` | Alternate lamp-intensity command | Redundant | `0x30` is already implemented and vessel-tested; transmitting both could create duplicate control traffic. |
| `0x81` | Course-computer setup state | Device-owned | This reports a real course computer's calibration/setup lifecycle. |
| `0x82` | Target waypoint name | Implemented | Managed as a passive four-character target announcement with duplicate suppression. |
| `0x83` | Course-computer failure/status | Device-owned | The plugin cannot truthfully report drive or auto-release status for a course computer. |
| `0x84` | Heading, autopilot course/mode, alarms and rudder | Device-owned | A composite authoritative autopilot state frame must come from the course computer; synthesizing it risks conflicts and false mode/alarm state. |
| `0x85` | Navigation to waypoint | Implemented | Managed as fresh, coherent, range-checked passive mode-5 guidance; it never engages Track mode or acknowledges an advance. |
| `0x86` | Autopilot keystroke | Safety boundary | Steering, mode, tack, and setup key commands are explicitly prohibited. |
| `0x87` | Set autopilot response level | Safety boundary | Changes steering behavior and requires deliberate helm control. |
| `0x88` | Autopilot calibration parameter report | Device-owned | Parameter state must be reported by the actual course computer, not inferred or impersonated. |
| `0x89` | ST40 compass heading and locked-steer state | Device-owned | Would compete with the installed heading source and also carries steering-lock state. |
| `0x90` | Device identification heartbeat | Device-owned | The bridge/plugin has no assigned Knauf device type and must not claim one. |
| `0x91` | Set rudder gain | Safety boundary | Directly changes autopilot steering response. |
| `0x92` | Set autopilot parameter | Safety boundary | Remote calibration writes are outside the passive boundary. |
| `0x93` | Enter autopilot setup | Safety boundary | Setup-mode entry is a remote-control operation. |
| `0x95` | Autopilot value-setting state | Device-owned | Composite setup state belongs to the course computer and has partially device-specific fields. |
| `0x99` | Compass variation | Implemented | Encoded from `navigation.magneticVariation`; east-positive Signal K radians are converted to west-positive SeaTalk whole degrees. |
| `0x9A` | Device version string | Device-owned | A SeaTalk hardware version frame is not an appropriate software-plugin identity mechanism. |
| `0x9C` | Compass heading and rudder position | Device-owned | Heading/rudder is already SeaTalk-originated on the vessel; retransmission would compete or loop, and rudder validity must come from the real sensor. |
| `0x9E` | Waypoint definition | Safety boundary | Injects waypoint coordinates and identity into the legacy navigation system; the plugin intentionally limits itself to passive current-target guidance. |
| `0xA1` | Destination waypoint information | Redundant | `0x82`/`0x85` cover the current passive target; multi-record destination-name injection adds compatibility and state risks. |
| `0xA2` | Arrival information | Safety boundary | Arrival-circle/perpendicular-passed state can drive alarms or waypoint transitions and needs authoritative course-provider semantics and explicit operator policy. |
| `0xA4` | Device identification query/response | Device-owned | Bus discovery belongs to real devices and requires a complete identity implementation, not a partial converter response. |
| `0xA5` | Detailed GPS/DGPS fix and satellite data | Redundant | `0x50`–`0x57` provide the selected interoperable GPS subset. Knauf documents several `0xA5` variants as unknown or observational, so emitting partial detailed state is not justified. |
| `0xA7` | Raystar 120 message, unknown meaning | Insufficient definition | Knauf records the frame but not its semantics. |
| `0xA8` | Guard alarm on/off | Safety boundary | Alarm creation and clearing is not generated without a dedicated, authoritative alarm integration. |
| `0xAB` | Guard alarm on/off | Safety boundary | Same restriction as `0xA8`; the relationship between the two forms is not sufficiently defined for safe generation. |

## Implementation policy

The plugin converts selected external Signal K values *to* SeaTalk1. It is not
a general SeaTalk device emulator. A command is not added merely because its
byte layout is known. Before a candidate can be implemented it needs:

1. an authoritative Signal K source and unit/sign convention;
2. a rule preventing retransmission of values originally received from the
   same SeaTalk bus;
3. a clear ownership and priority policy when a real SeaTalk talker exists;
4. range, freshness, rate-limit, and malformed-input behavior;
5. encoder vectors and a physical-bus vessel test.

Autopilot keys, steering modes, calibration writes, alarm acknowledgments,
MOB actions, and waypoint-advance/arrival commands remain outside the project
safety boundary even if a Signal K source becomes available.
